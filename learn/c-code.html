Four bugs, with the logged numbers


    

      Bug 1 · 58 GB "allocated" on a 16 GB GPU
      
Autograd kept every micro-batch alive

      
The first statistics pass crashed in layer 0 with "58.64 GiB is allocated by PyTorch". Weights loaded with
        load_state_dict(..., assign=True) keep requires_grad=True, and run_layer was not
        inside torch.no_grad(), so PyTorch recorded a backward graph for every micro-batch and kept all their
        activations. On Windows the excess silently spilled into system RAM, which is why the number could exceed the GPU.

      
layer.requires_grad_(False)   # build_layer(): inference only
@torch.no_grad()              # on Streamer.run_layer / embed / nll

    


    

      Bug 2 · memory grows 1.8 GB per layer
      
A reference cycle kept every layer on the GPU

      
layer.mlp.forward = lambda x, mlp=layer.mlp: … stores a function on the module that refers back to the
        module. Reference counting can never free such a cycle, so each 1.7 GB layer stayed on the GPU until Python's cycle
        collector happened to run. The healing run's peak memory, as logged, then the fixed run:

      

      
ref = weakref.ref(layer.mlp)                       # patch_moe() in moe_stream.py
layer.mlp.forward = lambda x: moe_forward(ref(), x, stats)

    


    

      Bug 3 · no error, just 30x slower
      
WSL/Windows spills VRAM into system RAM instead of failing

      
While bug 2 was still present, the run-1 statistics pass did not crash: whenever memory went past 16 GB the Windows
        driver quietly backed it with system RAM over PCIe ("sysmem fallback"), and some layers took 145 s instead of 5 s.
        The evidence: the GPU sat at 15.9 of 16 GB and 100% busy while the disk was idle (5.2 GB/s uncached when tested). Capping PyTorch below the physical VRAM turns that slowdown into a clear error,
        and after the fix every layer takes about 4–5 s. Seconds per layer, run 1 against run 2:

      

      
os.environ.setdefault("PYTORCH_CUDA_ALLOC_CONF", "expandable_segments:True")
torch.cuda.set_per_process_memory_fraction(0.85)   # VRAM_FRACTION, in Streamer()

    


    

      Bug 4 · the same model, two different answers
      
GPU atomic additions made every run slightly different

      
Step 5 measured the unchanged model twice as a control, and the two runs disagreed by up to 0.15% perplexity per
        domain (geometry +0.147%, physics −0.046%), more than deleting one expert changed. moe_forward added each
        token's 8 expert outputs with index_add_, which on a GPU uses atomic additions: threads add into the
        same memory in whatever order they finish, and in bf16 the rounding depends on the order. 40 layers amplify a
        last-bit difference into a measurable one. Nothing crashed and every earlier result was "right" to within that
        noise, which is why it went unnoticed until an experiment needed more precision. After the fix the repeat run
        matched to the last bit (0.0000% on every domain).

      
contrib = torch.empty_like(ys)
contrib[order] = ys * weight[:, None]               # each (token, slot) back in its place
out = contrib.view(-1, top_k, hidden).sum(dim=1)    # fixed order: bit-identical on every run

    

  


  

    
Three more habits that saved time

    
Detach long jobs with setsid nohup … > logs/x.log 2>&1 &. A statistics pass once died at
      layer 10 because the terminal session ended. And pkill -f pattern kills your own shell if the pattern
      appears in its command line; use pkill -x llama-server or a PID.

    
Check before you build on it. The custom MoE forward was compared against the HF implementation on a real
      layer, the on-disk checkpoint had to reproduce the virtual-pruning perplexity (5.915 vs 5.916), and the healing undo
      was verified by comparing router rows with the original.

    
Measure the measurement. Before trusting a small effect, run the unchanged thing twice and look at the
      difference. That control found bug 4; the gradient check in step 3 is the same idea for training.
