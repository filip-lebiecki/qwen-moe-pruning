Chapter 15

What sets the speed

Reading a prompt and writing an answer are different jobs for a GPU. Reading is limited by arithmetic; writing, one token at a time, is limited by how fast the weights can be fetched from memory. That makes generation speed something you can estimate with a calculator, and explains why a MoE is fast, why spilling out of VRAM is a cliff, and what serving several users at once buys.

Try it: estimate the speed of any model on any hardware

Ceiling = bandwidth ÷ (active parameters x bits ÷ 8). Real runs reach roughly 40–70% of it; this project's 19 B Q4_K_M reached 46% (212 of 463 tokens per second). It ignores the KV cache, which also has to be read for every token and matters at long contexts.

What to remember

Prefill is compute-bound, decode is memory-bound. A prompt of 1,621 tokens was read in 0.29 s; 256 new tokens took 1.20 s. When generating, the GPU waits for weights, not for arithmetic.

Tokens per second ≤ memory bandwidth ÷ bytes read per token. The 19 B Q4_K_M reads 1.80 GiB per token: the routed experts are 86% of the file but only 32% of what one token touches, which is why a MoE with 3 B active parameters runs like a 3 B model while knowing like a much bigger one.

Spilling is a cliff, batching is a slope. Weights read over PCIe come about 28x slower than from VRAM. Several requests at once share each weight read, so total throughput rises (182 → 488 tokens per second at 16), but a MoE gains less than a dense model because each request wants its own experts.
